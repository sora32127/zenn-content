# はじめに

最近、社内ドキュメントや自分用メモをLLMに読ませて作業させる機会が増えた。

その中で、次の問題に何度もぶつかった。

- 人間には読みやすい文書なのに、LLMが重要な制約を落とす
- 文章としては綺麗なのに、実行結果が安定しない

つまり、**Human-readableに最適化してもAI-readableにはならない**。

この記事は、この問題に対して自分が今どう運用しているかのメモ。

# TL;DR

- 人間向けに読みやすい文章と、AIが取りこぼしにくい情報は別物
- まずは「AIが読める場所に、制約と前提を欠けなく置く」ことを優先する
- 構造化や文体の綺麗さは、その後で十分

# 何が問題だったか

例えば、設計メモに次を自然文で書いていた。

- 推奨フロー
- 例外ケース
- やってはいけない操作

人間が読むと理解できるが、LLMは「推奨フロー」だけ拾って、禁止事項や例外を落とすことがあった。

結果として、

- 余計な手戻り
- 余計なレビュー
- 余計なトークン消費

が発生した。

# 試したこと

## 1. まず制約を書く

文章の導入より先に、次を先頭に置くようにした。

- 禁止事項
- スコープ外
- 優先順位

これだけで、出力のブレがかなり減った。

## 2. 情報の置き場所を固定する

「どこかに書いてある」をやめて、参照元を1箇所に寄せた。

- 重要仕様は1ファイルに集約
- 周辺文書からはリンクで参照

この形にしてから、AIが古い情報を参照する頻度が下がった。

## 3. 構造化は後回しにする

以前は先に綺麗な構造化をやろうとしていた。

ただ実務では、

1. AIが読める場所に情報を置く
2. 欠落をなくす
3. 必要なところだけ構造化

の順番の方がうまくいった。

# メタデータの扱い

本文と同じくらい、次のメタ情報が効く。

- 更新日
- 信頼度（確定/暫定）
- 対象（人間向け/AI向け/両方）

特に「暫定情報」であることを明示するだけで、AIの断定的な誤答を減らせた。

# 今の運用ルール

今は次だけ守るようにしている。

1. 文体を整える前に制約を書く
2. 重要仕様の参照元を固定する
3. AIが読めない場所（口頭・流れるチャット）に重要事項を残さない
4. 更新日と信頼度を残す

派手ではないけど、実務ではこれが一番効いている。

# おわりに

Human-readableを突き詰めること自体は間違っていない。

ただ、LLMと協業するならそれだけでは不足する。

自分の今の結論はこれ。

> 綺麗に書くより、AIが取りこぼさないように置く。

同じ問題に当たっている人の参考になればうれしい。
