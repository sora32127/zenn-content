# はじめに

最近、ドキュメントの書き方をかなり変えた。

理由はシンプルで、LLMを実務に入れると次の事実が見えてくるからだ。

> 人間向けに読みやすい文書を作っても、AIが読みやすいとは限らない。

これは「文章力が足りない」という話ではない。最適化対象が違う、という話だ。

この記事では、データエンジニアとして私が何を捨てて、何を残しているかを書く。

# 立場

最初に誤解を避けたい。

- 人間向けの可読性は大事
- でも、それだけではAI運用は回らない
- だから **AIアクセシビリティ** を別軸で設計する

ここで言うAIアクセシビリティは、yuisekiさんの問題提起に近い。「アクセシビリティの対象を人間だけに固定しない」という発想だ。

# 自然文へのこだわりは、時々ノイズになる

私は以前、自然文として綺麗に書くことを優先していた。

でもLLM運用では、綺麗な文章より次が効く。

- 何をしてはいけないか
- 何を優先するか
- 例外条件は何か
- どこまでが今回のスコープか

この4つがないと、文体がどれだけ美しくてもAIは普通に外す。

逆に、箇条書きの荒いメモでも、制約が密なら意外なほど安定する。

# 構造化は「最初にやるべきこと」ではない

データエンジニアとして言いづらいけど、最近はこう考えている。

1. まず、AIが読める場所に情報を置く
2. 欠落なく置く
3. その後で必要な分だけ構造化する

「先に綺麗にモデリング」は気持ちいい。
でも、AIが参照しない場所に完璧な構造を作っても、実務価値はゼロになる。

# メタデータの価値は上がる

本文より効くことがあるのがメタデータだ。

最低限、次は入れておくとかなり変わる。

- 更新日
- 目的
- 優先度（must/should/may）
- 禁止事項
- 信頼度（確定/暫定）

人間は文脈補完がうまいけど、AIは補完を外す。だから補完させない。

# 「人間が読まない」ではなく「AIが読めない」が問題

最近の実務で一番効いた気づきはこれだった。

- 誰も読まない場所にある情報は、あとで読めばいい
- **AIが読めない場所にある情報は、最初から無いのと同じ**

会議の口頭前提、Slackの流れたスレ、個人メモだけにある仕様。
これらはAI運用の観点では欠損データになる。

# 私が今やっている運用ルール

実際には、次の5つだけ守るようにしている。

1. 文章を整える前に、制約と禁止事項を書く
2. 重要仕様は1ファイルに集約し、参照先を固定する
3. 人間向け説明とAI向けメモを分ける
4. 更新日と信頼度を必ず残す
5. AIが参照しない場所に重要情報を置かない

派手ではないけど、これでプロンプトの再現性はかなり上がった。

# おわりに

Human-readableを突き詰めること自体は、これまで正しかった。

でも、AIと協業するならそれだけでは足りない。

必要なのは「読みやすさ」一点勝負ではなく、
**AIが取りこぼさない情報配置**まで含めた設計だと思う。

私自身まだ試行錯誤中だが、今のところ結論はこれで固い。

> 綺麗に書くより、取りこぼさせないように置く。
